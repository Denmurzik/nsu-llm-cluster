# Доставка весов: зеркало Hugging Face, кэш тензоров, долгий старт

Большая модель на классе весит сотни гигабайт. Чтобы каждая нода не качала её из интернета, а перезапуск группы не гнал веса
по сети повторно, веса проходят три звена:

1. **Зеркало Hugging Face на главном** (под `hf-mirror`). Каждый файл скачивается из интернета один раз, затем раздаётся нодам
   по LAN.
2. **Диск ноды** (`/var/lib/llm-models`). Файл модели нужен только репликам и лидерам split-групп; rpc-серверы его не видят.
3. **Кэш тензоров rpc-серверов** (`ggml-rpc-server -c`, `/var/lib/llm-models/rpc`). При повторной загрузке лидер передаёт по
   сети только хэши. Почему так, описано в `docs/research/big-models.md`, разделы 1, 4 и 7.

## Зеркало

### Как устроено

- Под `hf-mirror` (`main/manifests/common-40-hf-mirror.yaml.tmpl`) работает на `llm-main`, в сети хоста. Он слушает
  `127.0.0.1:8090` (`HF_MIRROR_PORT`). Код лежит в `main/hf_mirror.py`: он использует только стандартную библиотеку Python
  и запускается интерпретатором `python3` из образа LiteLLM. Этот образ уже есть на главном и входит в офлайн-набор
  `run-main --airgap`.
- Caddy отдаёт зеркало по адресам `https://<MAIN_ADVERTISE_IP>/hf/` и `https://<PUBLIC_HOSTNAME>/hf/`, снимая префикс `/hf`. Для
  этого пути нет лимита тела запроса и нет буферизации. Ноды по умолчанию ходят по IP: на ПК класса имя часто не резолвится, а
  внутренний CA Caddy выдаёт сертификат и на IP. Со своим сертификатом (`run-main --certs`) ноды ходят по имени: такой сертификат
  обычно выдан только на имя.
- Инференс-поды (реплики, лидеры split, vLLM) получают:
  - `HF_ENDPOINT=https://<MAIN_ADVERTISE_IP>/hf/c/<имя ноды>` (адрес из `HF_MIRROR_URL`, если он задан); часть `/c/<имя ноды>`
    нужна для отчёта о прогрессе;
  - `HF_TOKEN` — ключ зеркала `HF_MIRROR_TOKEN` (`hf_` и 40 hex-символов; llama.cpp отправляет только токен такого вида).
    Настоящий `HF_TOKEN` остаётся на главном, им пользуется само зеркало;
  - корневой сертификат главного из ConfigMap `llm-ca` (`/etc/llm-ca/bundle.crt`: системные CA и CA главного). Его пишет
    `entrypoint.sh`, как только у Caddy появился корневой сертификат, или сразу, если у `--certs` есть `ca.crt`.
    `serve-llama.sh` выставляет `SSL_CERT_FILE` и `CURL_CA_BUNDLE`, если файл есть. Публичный сертификат без `ca.crt`
    проверяется системными CA.
- rpc-подам зеркало не нужно: им модель передаёт лидер.
- Standalone-ноды получают адрес зеркала (`hf_endpoint`, тоже с `/c/<имя ноды>`) и ключ (`hf_token`) в `desired` ответа на
  heartbeat. CA главного у них уже есть: `registrar.sh` сохраняет `/ca.crt` и собирает рядом `bundle.crt` (системные CA и CA
  главного). Если зеркало не отвечает на `/_mirror/health`, `serve-llama.sh` качает модель напрямую со своих `HF_ENDPOINT`
  и `HF_TOKEN` ноды (`HF_FALLBACK_*`) и пишет об этом в лог. При `HF_MIRROR_ENABLED=false` поле пустое, и нода работает
  как раньше.

Что зеркало умеет:

| Возможность | Как |
|---|---|
| `HEAD` и `GET /<owner>/<repo>/resolve/<ревизия>/<путь>` | Отвечает `200` без перенаправления. Заголовки `Content-Length`, `ETag` и `X-Linked-Etag` (sha256 LFS-файла), `X-Linked-Size`, `X-Repo-Commit`, `Accept-Ranges: bytes`. Заголовки Xet убраны, поэтому huggingface_hub качает обычным HTTP. |
| `Range`, докачка | `206` для `bytes=a-`, `bytes=a-b`, `bytes=-n`; `416` за концом файла. Запрос на диапазон во время скачивания ждёт своих байтов. |
| Один поток на файл | 15 нод, одновременно запросившие один файл, получают его из одного скачивания: каждая читает растущий `.part`. |
| Докачка самого зеркала | Прерванное скачивание продолжается с места обрыва, в том числе после перезапуска пода: `Range` к Hugging Face, если `ETag` совпал. |
| Метаданные | Проксируются только `GET /api/models/<repo>`, `/refs`, `/tree/<ревизия>[/<путь>]?recursive=…` и `/revision/<ревизия>` — то, что читают llama.cpp и huggingface_hub; остальной API Hugging Face получает `403`. Последний удачный ответ сохраняется (не больше 2000 ответов, старые удаляются). Ссылки `Link` (постраничный вывод) переписываются на адрес зеркала. |
| Шардированные GGUF | Каждая часть `-0000N-of-0000M.gguf` — отдельный файл. `serve-llama.sh` качает части через `resolve/<commit развёртывания>/` (без фиксации — `resolve/main/`), а `--hf-repo` использует `refs`, `tree` и `resolve/<commit>`. |
| Зафиксированный коммит | Портал фиксирует коммит `main` при создании развёртывания и при смене модели (`revision`, кнопка «Обновить до последней версии» на странице развёртывания), ноды качают `resolve/<sha>`. Кэш зеркала хранит один файл на путь, без ревизии: файл, скачанный из другого или неизвестного коммита, сверяется с Hugging Face сразу (тот же `ETag` — отдаётся из кэша, другой — скачивается заново). Пока идёт скачивание другой ревизии того же файла, запрос к коммиту проходит к Hugging Face напрямую, без кэша. Два развёртывания одного файла на разных коммитах поэтому перекачивают его друг за другом; держите их на одном коммите. |
| Обновлённый файл | Раз в час (`HF_MIRROR_REVALIDATE_S`) зеркало сверяет `ETag` скачанного файла с Hugging Face. Если файл изменился, он скачивается заново. Запрос к другому коммиту (`resolve/<40 hex>/…`), чем тот, из которого файл скачан, сверяется сразу. Без связи с Hugging Face отдаётся то, что есть, и следующая сверка ждёт снова час. |
| Лимит и LRU | Под лимитом `HF_MIRROR_MAX_GIB` скачанные файлы (`cache/`) и незавершённые скачивания. Каждое идущее скачивание заранее держит место под свои оставшиеся байты, поэтому параллельные части шардов не переполняют диск. Новому файлу зеркало освобождает место: удаляет давно не использованные файлы и брошенные `.part`. Файл, который сейчас отдаётся или пишется, не трогается. Файл больше лимита сразу получает `507` «Файл больше лимита кэша зеркала…» и ничего не вытесняет. Если места не хватает и после очистки — `507` «Кэш зеркала заполнен…», если кончился диск во время записи — `507` «На томе зеркала кончилось место…». |
| Зависшее скачивание | Клиент, который ждёт байтов, ждёт, пока скачивание движется; через 5 минут без новых байтов (`STALL_S`) соединение закрывается, и клиент докачивает по `Range`. |

Какие запросы делает клиент:
- llama.cpp b12033 с `--hf-repo`: `GET api/models/<repo>/refs`, затем `GET api/models/<repo>/tree/<commit>?recursive=true`,
  затем `HEAD` и `GET <repo>/resolve/<commit>/<файл>` с `Range` при докачке (`common/hf-cache.cpp`, `common/download.cpp`).
  Развёртывание с зафиксированной версией (все новые, задача 2-15) и модели из нескольких файлов `serve-llama.sh` скачивает сам из
  `resolve/<commit>`: `curl -C - --retry 100 --retry-all-errors --retry-delay 2 --retry-max-time 300`, а если curl сдался, но добавил байты,
  скрипт запускает его снова. Оборванный поток (нестабильная сеть до главного) поэтому не останавливает загрузку, а попытка без
  прогресса (404, неверный ключ) завершает под, и kubelet перезапускает его. Старые развёртывания без зафиксированной версии
  по-прежнему качает llama.cpp (`--hf-repo`); кнопка «Обновить до последней версии» фиксирует версию.
  Один файл качается одним последовательным `GET` (`Range` только с места обрыва, `common/download.cpp:186-196`),
  разные файлы (шарды) — параллельно (`common_download_run_tasks`, `:868-885`).
- `serve-llama.sh` для частей и для любого файла зафиксированного коммита: `HEAD -L` и `GET -C -` на `resolve/<commit или main>/<файл>`.
- huggingface_hub (vLLM): `api/models/<repo>/revision/<rev>`, `HEAD` и `GET` на `resolve`.

### Настройки (`.env` главного)

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `HF_MIRROR_MAX_GIB` | 500 | Лимит кэша зеркала в ГиБ. Администратор меняет его на странице «Настройки» (`hf_mirror_max_gib`): портал кладёт значение в ConfigMap `hf-mirror-settings`, зеркало читает его при запуске (`HF_MIRROR_MAX_GIB_OVERRIDE`, сильнее `.env`; сброс к `.env` пишет в ConfigMap пустое значение, и зеркало берёт `HF_MIRROR_MAX_GIB`), кнопка «Перезапустить зеркало» применяет его. |
| `HF_MIRROR_PORT` | 8090 | Порт зеркала на `127.0.0.1` главного. |
| `HF_ENDPOINT` | `https://huggingface.co` | Откуда качает зеркало. Портал ходит туда сам, только если зеркало выключено. |
| `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` | — | Прокси для выхода зеркала в интернет. |
| `HF_TOKEN` | — | Токен Hugging Face для закрытых репозиториев. Используется только на главном. |
| `HF_MIRROR_ENABLED` | `true` | `false`: поды и инспектор портала ходят на Hugging Face сами, с `HF_TOKEN` (как до зеркала). |
| `HF_MIRROR_URL` | `https://<MAIN_ADVERTISE_IP>/hf`; со своим сертификатом (`--certs`) `https://<PUBLIC_HOSTNAME>/hf` | Адрес зеркала для нод. Сертификат должен покрывать этот адрес: внутренний CA Caddy выдаёт сертификат и на `MAIN_ADVERTISE_IP`, свой сертификат обычно только на имя. Если свой сертификат выдан и на IP, а имя на нодах не резолвится, задайте `HF_MIRROR_URL=https://<IP главного>/hf`. |
| `MODEL_LOAD_MBPS` | 40 | Скорость одного пода (МБ/с) для бюджета старта, см. ниже. |
| `RPC_CACHE_MAX_GIB` | 64 | Лимит кэша тензоров на каждой ноде, 0 — без лимита. |

`HF_MIRROR_TOKEN` создаётся при первом запуске и хранится в `/var/lib/llm/secrets.env`, задавать его не нужно.

### Том и офлайн-режим

Файлы зеркала лежат в томе Docker `llm-main-hf`. `run-main.sh` и `run-main.ps1` монтируют его в главный контейнер как
`/var/lib/llm-hf`, под зеркала видит его как `/data`. `--uninstall` удаляет и этот том.

```
/var/lib/llm-hf/
  cache/<owner>/<repo>/<путь в репозитории>     скачанные файлы; отдаются для любой ревизии, под лимитом, LRU
  offline/<owner>/<repo>/<путь в репозитории>   файлы, положенные руками; отдаются первыми, не под лимитом, не удаляются
  models/local/<имя>/<файл>                     свои модели портала («Мои модели», docs/local-models.md): репозиторий local/<имя>
  models/*.gguf                                 каталог для файлов, которые портал сам разложит по models/local/
  .uploads/<id>.part                            загрузки через портал, ещё не законченные
  .mirror/state/<owner>/<repo>/<путь>.json      ETag, коммит, размер, время последнего использования скачанного файла
  .mirror/parts/<id>.part, <id>.json            скачивания, по паре на каждое; продолжаются после перезапуска
  .mirror/api/<sha1>.json                       последние ответы API метаданных
  .mirror/prefetch.json                         список заданий «Скачать заранее»; незаконченные продолжаются после перезапуска
```

Если у главного нет интернета, администратор кладёт файлы в `offline/` руками, сохраняя путь внутри репозитория:

```bash
# на машине с интернетом
huggingface-cli download unsloth/DeepSeek-R1-GGUF --include 'DeepSeek-R1-UD-IQ1_S/*' --local-dir ./DeepSeek-R1-GGUF
# на главном: копия в том через контейнер главного
docker exec llm-main mkdir -p /var/lib/llm-hf/offline/unsloth
docker cp ./DeepSeek-R1-GGUF llm-main:/var/lib/llm-hf/offline/unsloth/DeepSeek-R1-GGUF
```

В развёртывании указывается тот же репозиторий и путь первого шарда, например
`DeepSeek-R1-UD-IQ1_S/DeepSeek-R1-UD-IQ1_S-00001-of-00003.gguf`.

Файлы, положенные руками:
- отдаются как скачанные, с `Range`;
- метаданные (`refs`, `tree`, `revision`, `X-Repo-Commit`, `ETag`) зеркало строит из каталога, когда Hugging Face недоступен
  или не знает такого репозитория. Поэтому можно завести и свой репозиторий, например `my/model`. Владелец `local`
  занят своими моделями портала: репозиторий `local/<имя>` зеркало отдаёт только из `models/local/<имя>/` и никогда не
  спрашивает о нём Hugging Face (подробно в [local-models.md](local-models.md));
- не удаляются по LRU, не сверяются с Hugging Face и не входят в лимит `HF_MIRROR_MAX_GIB` (место на диске они, конечно,
  занимают: зеркало держит свободным 1 ГиБ сверх своих файлов).

Инспектор моделей портала (список файлов, заголовок GGUF для оценки памяти) тоже ходит через зеркало. Поэтому развёртывание
модели, положенной руками, создаётся и без интернета. Заголовок GGUF портал читает ограниченным `Range` (`bytes=0-N`): такой
запрос к файлу, которого в зеркале нет, зеркало передаёт в Hugging Face напрямую и ради него файл целиком не качает.
Пока под зеркала не отвечает, инспектор с предупреждением в логе портала ходит на `HF_ENDPOINT` напрямую, с `HF_TOKEN`.
Ответ «не найдено» от зеркала остаётся в силе: зеркало уже спросило Hugging Face.

## Кэш моделей в интерфейсе

Страница «Кэш моделей» (Администрирование, рядом с «Мои модели») показывает, что лежит в `cache/`, и качает файлы заранее.
Это отдельная страница, а не вкладка «Мои модели»: свои модели лежат в `models/local/`, не входят в лимит и не удаляются, а кэш
заполняется скачиванием с Hugging Face, ограничен `HF_MIRROR_MAX_GIB` и чистится по LRU. У этих файлов разные правила удаления
и разные цифры места, поэтому одна таблица путала бы их.

Что есть на странице:
- **Занятое место.** Занято из лимита кэша (файлы и незаконченные скачивания), сколько можно скачать ещё (меньшее из остатка
  лимита и свободного места тома за вычетом запаса, который зеркало держит: 15 % тома, не меньше 1 ГиБ), свободно на диске.
- **Файлы по репозиториям.** Размер, коммит, время, когда файл последний раз отдавался ноде, состояние («В кэше»,
  «Скачивается, 37 %», «Недокачан»: часть, оставшаяся от оборвавшегося скачивания) и отметка «Используется развёртыванием X».
- **Удаление.** Кнопка «Удалить» файла или всего репозитория с подтверждением. Она недоступна, а причина написана в строке,
  если файл нужен развёртыванию (любому, и выключенному: его веса ноды возьмут при включении), сейчас отдаётся нодам или
  скачивается. Портал проверяет это и сам (`409`), не только кнопка. Файлы развёртывания портал считает по репозиторию,
  всем частям многофайлового GGUF, проектору и черновой модели; для vLLM занят весь репозиторий.
- **Скачать заранее.** Репозиторий Hugging Face, «Найти файлы», затем выбор файлов GGUF (многофайловая модель одним пунктом,
  со всеми частями) и проекторов изображений. Если выбрано больше, чем свободно в лимите, страница предупреждает, что зеркало
  удалит давно не использованные файлы, а если больше самого лимита, не даёт начать.
- **Загрузки.** Очередь и ход: процент, скачано из полного размера, скорость, сколько осталось, ошибка. «Отменить» останавливает
  скачивание, «Убрать» и «Убрать завершённые» чистят список. Пока что-то качается, страница обновляется раз в 2 секунды, иначе
  раз в 10.
- **На странице развёртывания** кнопка «Скачать заранее» ставит в очередь веса этого развёртывания: файл модели (все части),
  проектор и черновую модель, каждый из своего зафиксированного коммита (`revision`, `draft_revision`). У развёртывания из
  своих файлов (`local/…`) кнопки нет: они и так лежат на главном.

Как работает скачивание заранее. Задание идёт тем же путём, что запрос ноды (`Mirror.download`), поэтому файл ложится в `cache/`
точно так же, с состоянием для LRU и сверкой `ETag`, а нода, которая запросила тот же файл в это время, получает его из того же
скачивания. Одновременно идут два задания (`PREFETCH_CONCURRENCY`), остальные ждут. Файл, который уже в кэше (или лежит в
`offline/`), закрывается сразу как «Уже в кэше», и его время использования обновляется. Список заданий хранится в
`.mirror/prefetch.json`: после перезапуска зеркала (и портала) незаконченные задания продолжаются, `.part` докачивается через
`Range`. Отмена оставляет `.part` (его можно докачать повторным заданием, а при нехватке места LRU уберёт его наравне с остальными файлами, по давности), но не
останавливает скачивание, которого ждёт нода: тогда задание лишь выходит из списка.

Внимание: LRU не знает о развёртываниях. Файлы развёртывания защищены от кнопки «Удалить», но не от вытеснения, когда кэш
заполнен: скачивание большой модели заранее может вытеснить давно не использованные веса другого развёртывания, и нода скачает
их снова. Держите `HF_MIRROR_MAX_GIB` больше суммы весов всех развёртываний.

### Админский API зеркала

Для портала, не для нод. Путь `/admin/…` требует ключ зеркала, как и всё остальное, и сверх того отвергается с `403`, если запрос
пришёл через Caddy (есть заголовки `X-Forwarded-*`) или с префиксом `/c/<нода>`: ключ зеркала есть и у нод, но управлять кэшем им
нельзя. Портал ходит на `http://127.0.0.1:8090` напрямую.

| Запрос | Что делает |
|---|---|
| `GET /admin/cache` | Файлы `cache/`: `repo`, `path`, `revision` (коммит), `size`, `total`, `mtime`, `last_served`, `downloading`, `partial`, `busy`; скачиваемые сейчас файлы и оставшиеся от умерших скачиваний `.part` тоже в списке. Итоги: `used_bytes`, `limit_bytes`, `disk_total_bytes`, `disk_free_bytes`, `disk_reserve_bytes`. |
| `DELETE /admin/cache/<владелец>/<репозиторий>[/<путь>]` | Удаляет файл (с состоянием и оставшимся `.part`) или весь репозиторий. `409`, если хоть один файл сейчас отдаётся или скачивается (тогда не удаляется ничего), `404`, если нечего удалять. |
| `POST /admin/prefetch` | `{repo, revision?, files[]}`, до 200 файлов, `revision` по умолчанию `main`. Ставит по заданию на файл, `202`. Файл, который уже в очереди или качается, возвращает то же задание. Репозитории `local/…` отвергаются. |
| `GET /admin/prefetch` | Задания: `id`, `repo`, `revision`, `path`, `state` (`queued`, `running`, `done`, `failed`, `cancelled`), `size`, `written`, `speed_bps`, `error`, `cached`, `created`, `started`, `finished`. |
| `DELETE /admin/prefetch/<id>` | Отменяет ожидающее или идущее задание, а у законченного убирает его из списка. Без `<id>` убирает все законченные. В списке остаются последние 100 законченных. |

API портала (администраторы, CSRF на изменяющих запросах) пересылает это в зеркало: `GET/DELETE /api/admin/cache…`,
`GET/POST/DELETE /api/admin/prefetch…` и `POST /api/admin/deployments/{id}/prefetch`. Если зеркало выключено
(`HF_MIRROR_ENABLED=false`) или не отвечает, они дают `503` с причиной.

## Кэш тензоров на нодах

`ggml-rpc-server -c` кладёт каждый тензор больше 10 МиБ в `$LLAMA_CACHE/rpc/<fnv1a64>` и никогда не удаляет. Флаг `-c` и
монтирование тома в rpc-под задаёт задача 2-2. Очистку делает `rpc-cache-gc.sh` в образе ноды: `serve-rpc.sh` запускает её
в фоне, проход повторяется каждые 10 минут. Проход удаляет файлы с самым старым временем использования (новейшее из
`atime` и `mtime`), пока кэш не станет меньше `RPC_CACHE_MAX_GIB` и на файловой системе не будет свободно хотя бы 10 %
(`RPC_CACHE_MIN_FREE_PCT`). Удалённый тензор лидер при следующей загрузке просто передаст заново.

Файлы моделей и весь кэш тензоров с ноды убирает очистка весов по кнопке и автоматически (`docs/deploy-class.md`, «Очистка весов моделей на нодах»).

В WSL2 `df` видит виртуальный диск ext4.vhdx с его предельным размером (по умолчанию 1 ТБ), а не свободное место на диске
Windows: проверка `RPC_CACHE_MIN_FREE_PCT` там Windows-диск не защищает. На ПК класса диск ограничивает только
`RPC_CACHE_MAX_GIB`, задавайте его с учётом реально свободного места.

## Части моделей на нодах

`serve-llama.sh` хранит части многофайловых GGUF в `$LLAMA_CACHE/<владелец>__<репозиторий>/`. Контроллер портала
записывает репозитории всех развёртываний (выключенные тоже) в ConfigMap `llm-model-repos`, а под читает список при старте
(переменная `KEEP_MODEL_REPOS`). При старте модели скрипт удаляет папки репозиториев, которых в списке нет, и пишет каждую
в журнал пода (`removing cached model …`). Свой репозиторий пода остаётся всегда. Не трогаются собственные файлы
моделей (`local__*`), кэш тензоров `rpc` и кэш vLLM `huggingface`. Без списка (ConfigMap ещё нет, или он пуст) ничего
не удаляется. Копия модели, которая ещё развёрнута, остаётся и на ноде, которую переназначили на другое развёртывание
(например, на бывшем лидере группы): освободить это место можно только вручную.

## Долгий старт

`startupProbe` инференс-пода даёт на старт `max(3600, 600 + 2 × размер / MODEL_LOAD_MBPS × 1,5)` секунд:
- двойка — веса проходят сеть дважды (зеркало → нода, затем лидер → rpc-серверы);
- 1,5 — запас.

Например, 200 ГБ при 40 МБ/с дают 15 600 с, то есть 4 ч 20 мин. Размер берётся из `meta.weights_bytes` развёртывания; пока
метаданных нет (Hugging Face был недоступен), бюджет считается для 100 ГБ.

`MODEL_LOAD_MBPS` — скорость одного пода. Реплики, которые качают одновременно, делят канал главного: при N репликах на 1 ГбЕ
это около 110 / N МБ/с, и при большой модели значение стоит уменьшить так же. Делить автоматически нельзя: число нод попало бы
в шаблон пода, и любое новое назначение перезапускало бы все реплики.

## Прогресс в интерфейсе

У llama-server нет процента загрузки по HTTP. Статус развёртывания (`GET /api/admin/deployments/{id}/status`, поле `progress`
у каждого инференс-пода) собирается из двух источников:

| Стадия | Признак |
|---|---|
| `downloading`, «Скачивание X %» | Под работает, `/health` не отвечает. X — байты, которые зеркало отдало этой ноде (`GET /_mirror/transfers`), к `meta.weights_bytes`. |
| `loading`, «Загрузка весов» | `/health` отвечает 503 (llama-server грузит веса, лидер split передаёт их rpc-серверам), либо файл уже скачан, а сервер ещё не поднялся. |
| `ready`, «Готов» | Под готов. |
| `starting`, «Запуск» | Под работает, но зеркало ему ничего не отдавало, и `/health` молчит. Так бывает при `HF_MIRROR_ENABLED=false` и в первые секунды старта с уже скачанной моделью. |

Отчёт о передачах хранится 6 часов после окончания.
