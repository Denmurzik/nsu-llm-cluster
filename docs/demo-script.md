# Сценарий демонстрации

Показываем весь путь: главный сервер на ноутбуке, нода `122b`, вход через NSU ID, каталог моделей, развёртывание и изменение модели в UI,
выпуск ключа, запросы со второго ноутбука, отказ ноды. Тайминги и скорости ниже измерены на этом же стенде (`docs/verification.md`),
GPU в демонстрации не участвует: GPU-путь на машинах класса не проверялся.

## Раскладка

| Устройство | Роль | Адрес |
|---|---|---|
| Ноутбук с Windows (Docker Desktop, WSL 8 GB) | главная | `<IP ноутбука>` в сети класса |
| `122b` (Ubuntu 24.04, i5-4570, 4 ядра, 192.168.3.200) | нода, CPU, k3s, bridge с `-p`; имя ноды в кластере `cbebupelkaserver` (имя хоста в нижнем регистре, в командах `--name`) | 192.168.3.200 |
| Второй ноутбук | пользователь: браузер и `curl` | `hosts` направляет `double.fresh.nsuts.ru` на `<IP ноутбука>` |

Дальше `<MAIN_IP>` обозначает `<IP ноутбука>`.

## До начала (подготовка за день)

1. Образы собраны и загружены: на ноутбуке `nsu-llm-main:0.1.0`, на `122b` `nsu-llm-node:0.1.0-cpu` (`docker load`).
2. `.env` заполнен: `OIDC_CLIENT_SECRET`, `ADMIN_EMAILS` с вашим e-mail, `PUBLIC_HOSTNAME=double.fresh.nsuts.ru`.
3. На втором ноутбуке: строка в `hosts` (`<MAIN_IP>  double.fresh.nsuts.ru`) и установленный CA (см. кадр 6).
4. Файл модели Gemma 4 E4B (4,7 ГБ) уже скачан на `122b` (том `llm-models`): тогда кадр 4 занимает ~40 с. Первое скачивание ≈5 ГБ
   с Hugging Face заранее не измерялось и может занять много минут, поэтому грейте кеш заранее.
5. Порты 443, 80, 6443 открыты на ноутбуке, 18080 и 18050 на `122b`. На ноутбуке с WSL2 mirrored: правило Hyper-V firewall и
   `hostAddressLoopback=true` (`docs/deploy-class.md`), нет входящих правил, блокирующих 443 (с другой машины должен отвечать
   `curl -k https://<MAIN_IP>/ca.crt`). Иначе второй ноутбук и standalone-нода до главного не дойдут.
6. Главный запущен заранее: первый запуск ~2–3 мин (128–196 с в тестовом прогоне), перезапуск ~30 с. В логе главного нет предупреждения
   «нет hairpin» (`docker logs llm-main`); если сеть меняли после старта, перезапустите главный.
7. NSU ID присылает `email_verified=false` (проверено вживую), поэтому для NSU ID в `.env` стоит `ADMIN_REQUIRE_EMAIL_VERIFIED=false`
   (как в `.env.example`), иначе администратор не получит разделов админки.

## Кадры

### 1. Главный на ноутбуке

Показываем: один контейнер `llm-main`, внутри k3s, шлюз и портал.

```powershell
.\main\run-main.ps1 -EnvFile .env
docker ps --format "table {{.Names}}\t{{.Status}}"
curl.exe -sk https://<MAIN_IP>/readyz
docker exec llm-main k3s kubectl get nodes -o wide
```

Ожидаем: `readyz` отвечает `{"db":true,"litellm":true}`, в списке один узел `llm-main`.
Первый запуск главного до `readyz` ~2–3 мин (128–196 с в тестовом прогоне, запускайте до показа), перезапуск ~30 с.

### 2. Нода 122b присоединяется

В UI на ноутбуке (под админом, после кадра 3 можно показать позже) раздел «Ноды» → «Подключение ноды», копируем команду.
На `122b`:

```bash
sudo ./node/run-node.sh --main <MAIN_IP> --token <токен>
docker ps --format 'table {{.Names}}\t{{.Status}}'
```

В «Ноды» на ноутбуке появляется нода `cbebupelkaserver` (имя хоста `122b` в нижнем регистре): ускоритель `cpu`, ёмкость, готовность. Показываем и узел в k3s:

```powershell
docker exec llm-main k3s kubectl get nodes --show-labels
```

Ожидаем метку `llm.nsu/accel=cpu`. Скрипт `run-node.sh` отрабатывает за ~15 с, нода Ready через ~10 с.

### 3. Вход через NSU ID

На втором ноутбуке открыть `https://double.fresh.nsuts.ru/`, нажать «Войти через NSU ID», ввести учётные данные в форме NSU ID, вернуться на портал.
Показываем: у обычного пользователя разделы «Модели», «Ключи», «Быстрый старт», «Playground», «Использование»; у админа (адрес из `ADMIN_EMAILS`) ещё «Развёртывания», «Ноды», «Пользователи».

### 4. Каталог моделей и первое развёртывание

Под админом: «Модели» показывает `gemma-4-e4b` со статусом, контекстом на запрос и режимом. «Развёртывания» → строка `gemma-4-e4b`:
нода `122b`, под, фаза, готовность. Кнопка «Логи» у пода показывает скачивание и загрузку модели.
Дожидаемся состояния «готово»: с файлом модели в кеше ноды под готов за ~40 с (`n_slots = 2, n_ctx_slot = 8192`).

### 5. Развёртывание и изменение модели в админке

Показываем, как меняется модель без конфигов и без перезапуска главного (нужна вторая нода, например нода на ноутбуке:
`sudo`-аналог для Windows: `.\node\run-node.ps1 -Main <MAIN_IP> -Token <токен>` в PowerShell от администратора).

1. «Развёртывания» → «Создать развёртывание».
2. «Репозиторий Hugging Face»: `ggml-org/gemma-3-270m-it-GGUF`, выбрать файл `gemma-3-270m-it-Q8_0.gguf`.
3. Имя развёртывания: `tiny`, «Режим»: «Реплики», «Ускоритель»: любой. «Контекст на запрос» 2048, «Параллельность» 2.
4. Смотрим панель «Оценка памяти»: веса, KV-кэш, ёмкость нод, рекомендация размера группы. Увеличиваем контекст до значения, которое не помещается,
   показываем предупреждение; возвращаем.
5. Выбираем ноду вручную (в блоке «Ноды», не включая «Назначать свободные ноды автоматически») и создаём.
   Нода, которую держит другое развёртывание, помечена «занята: <имя>», и форма спросит подтверждение, прежде чем её забрать.
6. Открываем `tiny` → редактирование → «Контекст на запрос» 4096 → «Сохранить»: под перекатывается, в «Модели» меняется контекст
   (новый `max_input_tokens`). Перекатка пода с заменой записи в шлюзе заняла 31 с на тестовой модели, 42 с на Gemma 4 E4B.
7. Показываем переключение «Режим» в «Разделение по нодам» (`split`) на двух нодах: для `split` в той же форме выберите «Ускоритель» `cpu` или `nvidia`
   (у развёртывания с ускорителем «любой» кнопка «Сохранить» остаётся недоступной). Появляются поды `rpc` и leader.
   Группа собирается за ~20 с. Скорость split на тестовой модели 270M по Wi-Fi 1,7–2,3 ток/с против 111 ток/с у `replicas`: покажите это
   как наглядный довод, что split нужен только моделям, которые не помещаются на ноду. Верните режим «Реплики».

### 6. Ключ и запросы со второго ноутбука

Установка сертификата и проверка имени (на втором ноутбуке):

```powershell
curl.exe -o ca.crt http://<MAIN_IP>/ca.crt
certutil -addstore -f Root ca.crt          # PowerShell от имени администратора
curl.exe https://double.fresh.nsuts.ru/readyz
```

В UI «Ключи» → «Создать ключ» → название `demo` → значение показывается один раз, копируем. Затем:

```powershell
$KEY = "sk-..."
curl.exe https://double.fresh.nsuts.ru/v1/models -H "Authorization: Bearer $KEY"
curl.exe https://double.fresh.nsuts.ru/v1/chat/completions -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" `
  -d '{\"model\":\"gemma-4-e4b\",\"messages\":[{\"role\":\"user\",\"content\":\"Расскажи про Новосибирск одним предложением\"}],\"stream\":true}'
```

Без установки CA: `curl.exe --cacert ca.crt …`. Через OpenAI SDK:

```python
from openai import OpenAI

client = OpenAI(base_url="https://double.fresh.nsuts.ru/v1", api_key="sk-...")
for part in client.chat.completions.create(model="gemma-4-e4b", stream=True,
        messages=[{"role": "user", "content": "Привет"}]):
    print(part.choices[0].delta.content or "", end="")
```

Показываем: ключ в UI с маской, счётчик в «Использование». Ключ действует и на модель `tiny`, созданную после ключа.
Чего ждать от Gemma 4 E4B на `122b`: первый токен через ~1,5 с, генерация ~6 ток/с на запрос (при двух одновременных по 3,9 ток/с, суммарно 7,5).
Длинный промпт (около 1 100 токенов — порядка 49 с до первого токена, ≈23 ток/с), не показывайте его залу. Лимит ключа по умолчанию 60 запросов в минуту: больше
вернёт 429.

### 7. Playground

«Playground» → выбрать модель `gemma-4-e4b` → сообщение «Объясни, что такое кластер» → ответ приходит потоком. Меняем «Максимум токенов в ответе»
(от 1 до 4096), отправляем ещё раз.

### 8. Отказ ноды под нагрузкой

Для отказоустойчивости нужны две ноды с одним развёртыванием (`replicas`, например `122b` и нода ноутбука). На втором ноутбуке запускаем нагрузку
(ключ `$KEY` из кадра 6):

```powershell
1..200 | ForEach-Object {
  curl.exe -s -o NUL -w "%{http_code}`n" https://double.fresh.nsuts.ru/v1/chat/completions -H "Authorization: Bearer $KEY" `
    -H "Content-Type: application/json" -d '{\"model\":\"gemma-4-e4b\",\"messages\":[{\"role\":\"user\",\"content\":\"Привет\"}],\"max_tokens\":32}'
}
```

В «Развёртывания» видно два backend. На `122b` останавливаем ноду:

```bash
docker stop llm-node
```

Показываем: backend исчезает из списка за ≤20 с (на стенде 13,4 с), запросы продолжают выполняться на живой ноде; в UI у развёртывания остаётся один
готовый backend. На стенде при 20 параллельных потоках неуспешных запросов не было (310 из 310). Лимит 60 запросов в минуту действует на
пользователя целиком (все его ключи вместе): для нагрузки в зале берите ключи нескольких пользователей или поднимите лимит этому
пользователю на странице «Пользователи», иначе увидите 429 из-за лимита, а не отказа ноды.
Возвращаем ноду: `docker start llm-node`, через ~30 с снова два backend.

### 9. Удаление ноды (по запросу зала)

```bash
sudo ./node/run-node.sh --uninstall --main <MAIN_IP> --name cbebupelkaserver --token <токен>
```

Нода пропадает из «Ноды»; хост остаётся в исходном состоянии (контейнер, тома и каталог данных удалены).

## Если что-то пошло не так

| Симптом | Что сделать |
|---|---|
| Браузер не доверяет сертификату | установить `ca.crt` (кадр 6) или открыть `http://<MAIN_IP>/ca.crt` и добавить в доверенные |
| NSU ID возвращает ошибку redirect | открывать UI по имени `double.fresh.nsuts.ru`; вход по IP переводит на это имя сам |
| Нода не появляется | проверить TCP 6443 и 443 с ноды к главному, `docker logs llm-node` |
| Модель долго не готова | «Логи» у пода: идёт скачивание; запасной вариант: заранее скачанная модель (подготовка, п. 4) |
| Нода пересоздана и не присоединяется («Node password rejected») | `--uninstall` с тем же `--name` и запуск заново; если узел остался на главном: `docker exec llm-main k3s kubectl delete node <имя>` |
| С другой машины 443 главного не отвечает, а 80 и 6443 отвечают | входящее правило Windows, блокирующее 443; запрет сильнее разрешения |
| В `docker logs llm-main` предупреждение «нет hairpin», в «Развёртывания» не открываются логи подов на другой машине | включить `hostAddressLoopback=true` и перезапустить главный: адрес выбирается при старте |
| Администратору недоступны разделы админки | адрес в `ADMIN_EMAILS`; для NSU ID `ADMIN_REQUIRE_EMAIL_VERIFIED=false` (NSU ID присылает `email_verified=false`) |
| Ответ модели пустой при малом `max_tokens` | рассуждения выключены по умолчанию (`--reasoning off`); не включайте `THINKING=on` перед показом |
