# Параллелизм на нескольких нодах: можно ли в общем виде, без настройки под каждую модель

Вопрос лектора: можно ли распараллелить работу LLM на несколько нод «в общем виде», без настройки под каждую задачу.
Документ разбирает вопрос по двум разным видам параллелизма, говорит, что Kubernetes даёт без настройки, а что нет, и приводит замеры.
Источники: `docs/research/inference.md` (§3), `docs/research/k3s-in-docker.md`, спецификация, реализация портала.
Расчёты, помеченные «расчёт», сделаны по формулам, не измерены. Остальные числа измерены на реальных машинах и приведены по
`docs/verification.md` (задачи 15 и 16). Результаты нагрузочного теста на 1000 пользователей добавляются отдельным разделом ниже.

## 1. Короткий ответ

Да, для двух случаев, и оба реализованы в портале одинаково для любой GGUF-модели без ручных конфигов:

1. **Модель помещается на ноду, нужна пропускная способность и отказоустойчивость**: режим `replicas` (data-parallel, копия на каждую ноду).
   Это общий случай и он масштабируется почти линейно.
2. **Модель не помещается ни на одну ноду**: режим `split` (model-parallel, разрезание по слоям через llama.cpp RPC на группы по `group_size` нод).
   Это тоже строится в общем виде, но цена выше, а результат зависит от сети и от самой слабой ноды.

Чего «в общем виде» не получается: подобрать оптимальные параметры (размер группы, контекст, формат квантизации, разбиение слоёв)
без знания модели и железа. Для этого портал даёт оценку памяти и подсказку, но выбор остаётся за человеком.

## 2. Два вида параллелизма

**Data-parallel (реплики).** Каждая нода держит полную копию модели и обслуживает свои запросы. Нет обмена между нодами при генерации,
пропускная способность растёт линейно с числом нод, отказ одной ноды не роняет остальные, балансировка проста (LiteLLM, `least-busy`).
Условие: веса и KV-кэш помещаются в память одной ноды.

**Model-parallel (разрезание модели).** Одна копия модели распределена по нескольким нодам.
- *Pipeline-parallel (PP)*: нода держит подряд идущие слои; между стадиями передаётся один вектор активаций на токен.
- *Tensor-parallel (TP)*: каждый слой делится между нодами; на каждый слой нужны коллективные операции (all-reduce).
- llama.cpp RPC (реализовано в портале) относится к послойному, PP-подобному разбиению, не к TP: сервер на первой ноде группы
  с `--rpc` на остальные раскладывает слои по устройствам пропорционально доступной памяти.

Разрезание выигрывает, только когда модель не помещается ни в одну ноду или нужен больший контекст. Цена: сетевая задержка на каждый
токен, связность отказов (упала одна нода, вся группа недоступна), требование однородных нод.

## 3. Что Kubernetes даёт «в общем виде»

Без настройки под конкретную модель:

| Возможность | Как используется в проекте |
|---|---|
| Метки узлов | `llm.nsu/accel=cpu\|nvidia`, `llm.nsu/vram-mib`; портал ставит `llm.nsu/deployment=<имя>`: нода принадлежит не более чем одному развёртыванию |
| Планирование по меткам | все объекты инференса выбирают узлы по `llm.nsu/accel` и `llm.nsu/deployment`, главный их не несёт |
| DaemonSet на ускоритель | режим `replicas`: `llm-<имя>-cpu`, `llm-<имя>-gpu` дают по поду на каждую назначенную ноду без ручного списка |
| Группы по RPC, управляемые порталом | режим `split`: DaemonSet `llm-<имя>-rpc-<accel>` плюс Deployment-leader `llm-<имя>-g<i>` на каждую полную группу готовых нод; состав группы записан у лидера (`llm.nsu/group-members`) и не меняется, пока все её ноды живы |
| Проверка готовности | readiness по `GET /health` (503 пока модель грузится); шлюз дополнительно проверяет здоровье сам, мёртвый backend уходит из LiteLLM за ≤20 с |
| Rolling update | смена контекста, параллельности или модели меняет `llm.nsu/spec-hash` в шаблоне пода, поды перекатываются по одному |
| Failover | под или нода пропали, backend исчезает из LiteLLM, запросы идут на живые ноды; в `replicas` группа не нужна |
| Постоянный кеш моделей | том `llm-models` на ноде: повторный старт не скачивает файл заново |
| Ограниченная очередь | у каждого бэкенда `parallel × QUEUE_FACTOR` запросов (слоты плюс ожидание), сверх неё шлюз отвечает 429 с `Retry-After` вместо таймаута; лимит считается в каждом процессе шлюза отдельно: `max(parallel, ⌈parallel × QUEUE_FACTOR / LITELLM_WORKERS⌉)`, чтобы один процесс мог занять все слоты и не отвечал 429 при свободном слоте |

Что остаётся настраивать под модель (`docs/research/inference.md` §3.3):

- размер группы `group_size` и однородность нод (портал рекомендует минимальный размер по оценке памяти, но не знает скорость сети);
- значения TP и PP: делители числа голов и слоёв (например, у Gemma 4 31B 16 KV-голов, TP=3 невозможен);
- контекст, `--gpu-memory-utilization` и аналоги, объём KV-кэша;
- формат и квантизация (GGUF против compressed-tensors), chat template, парсеры tool calling и reasoning;
- разбиение слоёв при неоднородных нодах (`--tensor-split`, `VLLM_PP_LAYER_PARTITION`) и сеть (NCCL, RDMA).

Готовые надстройки для LLM на Kubernetes существуют (`kubernetes-sigs/gateway-api-inference-extension`, `llm-d`, `vllm-project/production-stack`);
их применимость к смеси vLLM и llama.cpp на нодах класса не проверялась и в проект не входит.

## 4. Разрезание по сети 1GbE: TP против PP (расчёт)

Нода класса имеет 1 Gbit/s Ethernet, прямых бенчмарков для этого железа нет, оценка сделана по формулам и помечена как расчёт.

- **TP через TCP нецелесообразен.** На слой приходятся два all-reduce; у модели с 60 слоями это 120 коллективных операций на токен по
  ~10,7 КБ (hidden 5376, BF16). Ограничением оказывается не пропускная способность, а задержка: при 0,3–1 мс на all-reduce только сеть даёт
  40–120 мс на токен, то есть 8–25 ток/с в лучшем случае для одного потока. Префилл 2 тыс. токенов: около 2,6 ГБ трафика, порядка 20 с на 1GbE.
- **PP подходит.** На границе стадий передаётся один вектор активаций на токен, десятки КБ на чанк префилла, 1GbE достаточно.
  Но при одном потоке стадии работают последовательно: скорость примерно как у одной GPU, выигрыш лишь в том, что модель помещается.
  Для заполнения конвейера нужна конкурентность (несколько запросов).
- **Следствие для проекта.** Режим `split` в портале реализован как PP-подобный (llama.cpp RPC), TP на 1GbE не предлагается.
  Скорость определяется самой слабой нодой группы и сетью (для смеси 4070 и i5-4570 это CPU-стадия).

**Измерено (тестовая модель 270M, `122b` и ноутбук по Wi-Fi, группа из двух нод):** `replicas` на одной ноде 111 ток/с (первый токен 0,16 с),
`split` 1,7–2,3 ток/с (первый токен 1,5–2,4 с), то есть в 48–65 раз медленнее. Аппаратура в сравнении разная: `replicas` работал на ноутбуке (standalone), а лидер `split` стоял на `122b`, слои лежали на `122b` и
на ноутбуке по Wi-Fi; это не сравнение «одна и та же нода против двух». На Wi-Fi это худший случай: каждый токен проходит
через RPC и сеть, а скорость определяет самый медленный участок. Расчёт для 1GbE не подменяется этим замером: он подтверждает вывод
(для модели, которая помещается на ноду, `split` не нужен), а не абсолютные цифры. Split Gemma 4 E4B не запускался: в WSL ноутбука
оставалось 5,4 ГБ памяти, меньше порога 6 ГБ.

## 5. Как оценивается память

UI и API админа считают оценку до создания развёртывания (`portal/app/catalog/estimate.py`):

1. **Веса** = размер GGUF-файла выбранного репозитория (без скачивания).
2. **KV-кэш** = `2 × n_layers × n_kv_heads × head_dim × (контекст_на_запрос × параллельность) × 2` байт (fp16). Числа слоёв, KV-голов и размерности головы
   берутся из заголовка GGUF (Range-чтение). Это оценка сверху: скользящее окно внимания (SWA) и общие KV-слои не учитываются,
   поэтому для Gemma 4 E4B реальный KV меньше.
3. **На ноду в группе из G нод** = `(веса + KV) / G + 512 МиБ` служебного запаса.
4. **Ёмкость ноды**: GPU = VRAM минус 1,5 ГиБ (метка `llm.nsu/vram-mib`; запас на CUDA-контекст, вычислительные буферы и рабочий стол Windows); CPU = 80 % RAM минус 1 ГиБ.
5. **Рекомендация** `group_size` = минимальное G, при котором G самых больших нод вмещают свою долю; если такого G нет, UI предупреждает,
   что модель не поместится.

Что измерено для Gemma 4 E4B Q4_K_M на `122b` (16 ГБ RAM): до запуска ноды было доступно 12 154 МБ, после загрузки модели
при 8192 × 2 доступно 7 973 МБ, при 16384 × 1 8 023 МБ; веса 4,98 ГБ. Разница порядка 4,2 ГБ включает кеш страниц файла модели и сам
процесс; на момент замеров на машине работали другие сервисы, поэтому это грубая оценка, а не RSS процесса. Построчное сравнение с
оценкой портала для этой модели не снималось. Порог в 2 ГБ свободной памяти соблюдён, переход на `Q3_K_M` не понадобился.

## 6. Замеры

Источник всех чисел: `docs/verification.md` (задачи 15 и 16). Стенд: `122b` (Ubuntu, i5-4570, 4 ядра, 16 ГБ, без GPU) и ноутбук
с Windows и Docker Desktop (11 vCPU и 8 ГБ у Docker VM) в одной сети; главный сервер на ноутбуке.

Замер на GPU (`newbar`, RTX 5090, standalone, llama.cpp CUDA, модель `ggml-org/gemma-3-270m-it-GGUF` Q8_0, контекст 2048, 2 слота):
генерация 982 ток/с, обработка промпта 1557 ток/с (второй запрос, 25 токенов). Это проверка работоспособности GPU-образа,
а не показатель целевой модели; GPU-путь на машинах класса не проверялся.

Gemma 4 E4B Q4_K_M, одна CPU-нода `122b`, потоковый запрос через шлюз (`max_tokens` 200, промпт 29 токенов; скорость генерации =
(токены − 1) / время от первого токена до конца). Клиент работал на самой `122b` и делил 4 ядра с моделью.

| Контекст × слоты | Параллельно | TTFT, с | Генерация на запрос, ток/с | Суммарно, ток/с |
|---|---|---|---|---|
| 8192 × 2 | 1 | 1,52 | 6,0 | 5,8 |
| 8192 × 2 | 2 | 1,95 / 2,47 | 3,9 / 3,9 | 7,5 |
| 8192 × 2, промпт 1 121 токен | 1 | 48,8 (промпт ≈ 23 ток/с) | 5,4 | не снималось |
| 16384 × 1 | 1 | 1,59 | 6,0 | 5,8 |
| 16384 × 1 | 2 | 0,53 / 34,3 (второй ждёт слот) | 6,0 / 6,1 | 6,0 |

Два слота по 8192 дают +29 % суммарной скорости (7,5 против 5,8 ток/с) ценой −35 % на запрос. Один слот отдаёт ту же скорость одному
пользователю, а второй одновременный запрос ждёт в очереди.

| Сценарий | Результат |
|---|---|
| Время до состояния «готово» | `gemma-4-e4b` на `122b` с файлом в кеше (том `llm-models`): 41 с; тестовая модель 270M с загрузкой с Hugging Face: 30–38 с. Первое скачивание ≈5 ГБ с Hugging Face на ноду не измерялось (файл был предзагружен) |
| Две ноды `replicas`, суммарная пропускная способность | для E4B на двух нодах не измерялась (E4B работал на одной ноде); `replicas` на двух нодах проверен на тестовой модели 270M: 2 бэкенда в шлюзе, smoke проходит. Для одной ноды при двух параллельных запросах суммарно 7,5 ток/с |
| Отказ ноды под нагрузкой (20 параллельных потоков, 4 ключа, `docker stop` ноды `122b` через 15 с) | backend исчез из `/api/models` через 13,4 с после остановки (цель ≤20 с); 310 запросов (60 до остановки, 50 за первые 20 с после, 200 позже), ни одного отказа: LiteLLM повторяет запрос на живом бэкенде. После `docker start` нода вернулась, через 31 с снова 2 бэкенда |
| Смена контекста у работающего развёртывания | `tiny-b` 1024 → 4096: под пересоздан, запись в шлюзе заменена (новый `max_input_tokens`) за 31 с; `gemma-4-e4b` 8192 × 2 → 16384 × 1: 42 с. Запрос на 13 899 токенов в контекст 4096 отклонён за 0,1 с (400, `exceeds the available context size`) |
| Формирование группы `split` (две ноды, 270M) | через 21 с после переключения режима: DaemonSet RPC на обеих нодах и лидер группы; в шлюзе один бэкенд; обратно в `replicas` за 30 с |
| `split` на CPU (270M, `122b` + ноутбук по Wi-Fi) против `replicas` | 1,7–2,3 ток/с против 111 ток/с (см. §4) |
| Скорость и потоки | на `122b` с `-t 4` 0,46 ток/с, с `-t 3` 5,6 ток/с (одно ядро занято посторонним процессом); тот же образ на Ryzen 9950X с ограничением 4 CPU 15 ток/с. Поэтому по умолчанию `THREADS = nproc - 1` |

Предупреждение о `tokens_per_s` в выводе `e2e/smoke.py`: скрипт считает чанки короткого ответа, это не замер производительности.
Таблицы выше получены отдельным скриптом с ответом в 200 токенов.

## Нагрузочный тест: 1000 пользователей

Подробности, все прогоны и причины в `docs/verification.md`, раздел «Задача 20c». Главный сервер на ноутбуке
(Docker Desktop, 11 vCPU, 7,9 ГБ), 4 воркера LiteLLM, 4 воркера API портала, генератор на 122b.

Сценарий A (только шлюз, 4 тестовых бэкенда, 32 токена по 500 мс), итоговый прогон A5:

| Показатель | Значение |
|---|---|
| одновременных потоков (макс.) | 993 |
| запросов / успешно / 5xx / 429 / таймауты | 13490 / 13490 / 0 / 0 / 0 |
| пропускная способность шлюза | 29,9 запроса/с, 958 токенов/с |
| TTFT p50 / p95 | 6,7 с / 13,7 с |
| портал p95 (`/api/me`, `/api/models`, `/api/keys`) | 0,033 / 0,035 / 0,035 с |
| память main | до 6,25 ГиБ, из них LiteLLM 4,8 ГиБ |

Узкое место: CPU воркеров LiteLLM. Все 4 заняты на 100%, TTFT в A5 и есть очередь к циклу событий воркера.
Предел растёт с `LITELLM_WORKERS`, но каждый воркер стоит около 780 МБ памяти.

Сценарий B (`tiny`, `parallel` 2, нода на том же ноутбуке):

* Перегрузка отдаётся как 429 с `Retry-After` и русским текстом.
* Таймауты клиента ушли после двух изменений: `QUEUE_FACTOR` по умолчанию 2 вместо 8 (один ожидающий запрос на
  слот) и 429 без внутренних повторов LiteLLM.
* На итоговом коде с клиентами, которые ждут `Retry-After` (прогон B6), из 26564 запросов 83 успешных,
  26478 ответов 429, 0 таймаутов и 3 ответа 5xx на пути к ноде в том же Docker Desktop. Ни один прогон B не
  прошёл все критерии.
* `/api/public/status` без входа при 70 запросах/с: 0 ошибок, p95 0,52 с.
* Ранних 429 из-за деления `max_parallel_requests` между воркерами почти нет: при 429 в полёте p50 = предел. Чтобы их
  не было и при малой нагрузке, лимит на воркер после прогонов не ниже `parallel` (один воркер занимает все слоты).
* Во время прогонов каждый 429 писал строку в `LiteLLM_SpendLogs` (около 2,6 КБ) и попадал в счётчик запросов портала.
  Теперь `general_settings.disable_error_logs: true`: отказы и ошибки в базу не пишутся и остаются в логах LiteLLM.

Для 1000 активных пользователей нужен главный сервер на отдельной машине с 8+ ядрами и 16 ГБ памяти
(`LITELLM_WORKERS` по числу ядер) и ноды отдельно от него. Пропускная способность моделей ограничена нодами:
CPU-нода с двумя слотами даёт около одного ответа в секунду на маленькой модели, остальные запросы получают 429.

## 7. vLLM и LWS: маршрут для GPU, и почему по умолчанию llama.cpp

**Почему llama.cpp по умолчанию.** Официальный чекпоинт `google/gemma-4-E4B-it-qat-w4a16-ct` для vLLM весит 11,5 ГБ (на GPU около 11,02 ГиБ):
таблицы эмбеддингов (в том числе PLE, 5,64 ГБ) остаются в BF16. На RTX 4070 с 12 ГБ почти не остаётся места под KV-кэш.
Выгрузка PLE на CPU решается патчем vLLM #62354, который на момент исследования не влит. Поэтому по умолчанию выбран llama.cpp:
GGUF Q4_K_M весит около 5 ГБ, один и тот же рантайм на CPU и GPU, тот же OpenAI API, и только на нём построено разрезание по RPC.

**vLLM в портале.** Экспериментальный движок (`vllm/vllm-openai:v0.32.0`), режим `replicas` на nvidia-нодах (DaemonSet `llm-<имя>-vllm`), помечен «не проверено».
Объекты проходят `kubectl apply --dry-run=server`; на реальной GPU-ноде запуск не проверялся.

**LeaderWorkerSet (LWS).** Это маршрут для разрезания в vLLM на GPU: `LeaderWorkerSet` с лидером и воркерами
(`--tensor-parallel-size`, `--pipeline-parallel-size`, `--nnodes`, `--node-rank`, `--master-addr`). Для одной GPU на узел и 1GbE разумно
`TP=1`, `PP=<число узлов>` (§4). В портале LWS не реализован: разрезание делается через llama.cpp RPC. Для vLLM-разрезания нужно отдельно
поставить CRD LWS и добавить генерацию его объектов; риски: окружение Windows/WSL2 как k8s-узел для NCCL между хостами (NAT WSL2),
общие KV-слои Gemma 4 E4B при разрезании по стадиям (не проверено). Для демонстрации разрезания лучше брать модель без KV-sharing (12B, 31B).

## 8. Выводы

- В общем виде, без настройки под модель: размещение (метки, DaemonSet, группы), балансировка, проверка готовности, rolling update, failover.
- Под модель и железо: размер групп, контекст, квантизация, chat template, сеть. Портал снижает цену этих решений оценкой памяти и рекомендацией
  `group_size`, но не отменяет их.
- На нодах класса (1GbE, разнородные машины) основной режим `replicas`; `split` нужен, когда модель больше памяти одной ноды, и работает как
  демонстрация общей формы, а не как производственное решение: на тестовой модели 270M он медленнее одной ноды в 48–65 раз (§4, §6).
- Измеренные ориентиры для Gemma 4 E4B на CPU-ноде класса (4 ядра): около 6 ток/с на одного пользователя, 7,5 ток/с суммарно при двух
  слотах, обработка промпта около 23 ток/с. Это даёт интерактивный диалог для небольшого числа пользователей на ноду; для большего числа
  нужны реплики и GPU, а перегрузка проявляется как очередь и ответ 429, а не как отказ.
- GPU-путь на машинах класса не проверялся; vLLM и LWS проверены только до `kubectl apply --dry-run=server`.
