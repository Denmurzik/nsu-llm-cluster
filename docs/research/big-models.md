# Большие модели на классе: что умеет llama.cpp RPC в b12033

Задача 2-1 плана `docs/superpowers/plans/2026-11-03-class-big-models.md`. Документ отвечает на вопросы задачи по исходникам
llama.cpp тега `b12033` (коммит `785322d17f2d`, 2026-11-01), который собирает `node/Dockerfile`. Ничего не собиралось и не запускалось.

Пометки:
- **Проверено** — прочитано в исходнике, цитата `файл:строка` дана относительно корня репозитория llama.cpp на этом теге.
- **Вывод** — следует из прочитанного кода, но не запускалось. Перед опорой на вывод его надо проверить вживую (раздел 12).
- Числа с пометкой «расчёт» получены по формуле из раздела 6. Это не замеры. Константы моделей (`n_embd`, `n_vocab`) взяты из
  `config.json` моделей, а не из исходников llama.cpp.

## 1. Пять фактов, которые сильнее всего меняют задачи 2-2 и 2-3

1. **Предел 16 бэкендов на лидера: группа — не больше 15 устройств.** Планировщик ggml держит не больше
   `GGML_SCHED_MAX_BACKENDS = 16` бэкендов (`ggml/src/ggml-backend.cpp:1163-1164`, `:2217`). Лидер создаёт бэкенд на каждое
   устройство модели плюс свой CPU (`src/llama-context.cpp:431-456`). `--tensor-split` принимает не больше 15 чисел
   (`common/arg.cpp:2801`, `llama_max_devices() == 16` в `src/llama.cpp:86-88`). Значит, 15 нод по два устройства (CUDA0 + CPU) —
   это 30 устройств, и на чистом b12033 такая группа не стартует. Варианты разобраны в разделе 3.
2. **У `ggml-rpc-server` нет лимита памяти устройства.** Флаги сервера: `-t`, `-d`, `-H`, `-p`, `-c` (`tools/rpc/rpc-server.cpp:96-106`).
   Устройство CPU на Linux сообщает `free = total = вся RAM` (`ggml/src/ggml-cpu/ggml-cpu.cpp:373-378`), то есть всю память WSL, без
   учёта cgroup. Поэтому размещение задаётся только на лидере, через `--tensor-split`. Значения — число слоёв на устройство
   (`src/llama-model.cpp:1679-1700`), а порядок устройств — порядок `--rpc`, внутри сервера — порядок `-d`. Портал (2-2) должен сам
   посчитать целые числа слоёв по байтам каждого слоя. Жёсткой границей служит лимит памяти пода rpc-сервера.
3. **Весь вес модели идёт через лидера.** Лидер читает GGUF со своего диска и отправляет каждый тензор на rpc-серверы
   (`src/llama-model-loader.cpp:1713-1749`), а rpc-ноды файл модели не видят. Кэш `-c` лежит в `$LLAMA_CACHE/rpc/<fnv1a64>` и
   хранит только тензоры весов больше 10 МиБ (`ggml/src/ggml-rpc/ggml-rpc.cpp:117-118`, `:847-849`, `:1748-1757`). Размер кэша ничем
   не ограничен, вытеснения нет. При повторной загрузке лидер всё равно читает и хэширует весь файл, а по сети идут только хэши.
   Для 2-3 это значит:
   - зеркало HF нужно только ноде лидера;
   - rpc-подам нужен том под кэш;
   - очистку кэша (LRU) делаем сами.
4. **Процент загрузки по HTTP не отдаётся.** Пока модель грузится, сервер отвечает 503 `Loading model` на все пути, кроме
   UI-ассетов, включая `/health` и `/slots` (`tools/server/server-http.cpp:308-326`). Процент виден только в режиме роутера: колбэк
   состояния подключается лишь при `role.is_managed_by_router()` (`tools/server/server.cpp:665-670`). Точки прогресса в лог тоже
   не пишутся, потому что сервер подменяет колбэк по умолчанию (`tools/server/server-context.cpp:1298-1302`). Прогресс для 2-3
   собираем сами: этап скачивания — по размеру файлов, этап загрузки — по логам лидера и rpc-серверов (раздел 7).
5. **KV-кэш DeepSeek V3/R1 и Kimi K2 (MLA) — только K, без V.** Если в GGUF есть `deepseek2.attention.key_length_mla` и
   `value_length_mla`, модель считается MLA (`src/llama-hparams.cpp:298-303`), и V-тензор кэша не создаётся
   (`src/llama-kv-cache.cpp:230-233`). На токен и слой это `key_length (576) × head_count_kv (1) × 2 байта`. Текущая формула портала
   `2 × n_layers × n_kv_heads × head_dim` (`portal/app/catalog/estimate.py:15-16`) завышает такой кэш вдвое. У GLM-4.5
   `block_count` включает MTP-слой, которого нет в кэше (`src/llama-model.cpp:3296-3301`).

Ещё два факта для 2-4:
- **Любой сбой RPC валит лидера целиком.** Это `GGML_ABORT` в `RPC_STATUS_ASSERT`, `ggml/src/ggml-rpc/ggml-rpc.cpp:31`, `:683-689`.
- **rpc-сервер обслуживает одного клиента за раз.** Цикл `accept` последовательный (`ggml/src/ggml-rpc/ggml-rpc.cpp:2823-2832`).

## 2. Несколько устройств в одном `ggml-rpc-server` и лимит памяти

**Проверено.**
- `-d, --device <dev1,dev2,...>` задаёт список устройств через запятую или `/` (`tools/rpc/rpc-server.cpp:126-141`). Имена ищутся
  без учёта регистра (`ggml/src/ggml-backend-reg.cpp:345-353`). У CPU имя `CPU` (`ggml/src/ggml-cpu/ggml-cpu.cpp:353-354`), у CUDA —
  `CUDA0`, `CUDA1` и так далее (`tools/rpc/README.md:68-72`). Неизвестное имя печатает список доступных устройств, и сервер
  завершается (`tools/rpc/rpc-server.cpp:167-181`).
- Без `-d` сервер отдаёт все не-CPU устройства. Только если их нет, он отдаёт CPU (`tools/rpc/rpc-server.cpp:185-202`). Сейчас
  `serve-rpc.sh` запускается без `-d`, поэтому GPU-нода отдаёт только CUDA0, и её RAM в split не участвует.
- Чтобы отдать видеопамять и RAM, нужен флаг `-d CUDA0,CPU`. Схема с `CUDA0` + `CPU` на одном хосте есть в
  `tools/rpc/README.md:16-19`. Сервер создаёт бэкенд на каждое устройство (`ggml/src/ggml-rpc/ggml-rpc.cpp:2782-2800`). Клиент
  получает число устройств командой `DEVICE_COUNT` (`:2495-2504`) и регистрирует их как `RPC<n>`, где `n` — сквозной номер по
  порядку `--rpc`, а затем по порядку `-d` (`:3156-3196`).
- `-t` задаёт потоки только для CPU-устройства (`tools/rpc/rpc-server.cpp:100`, `ggml/src/ggml-rpc/ggml-rpc.cpp:2794-2799`).
- **Флага лимита памяти нет.** Полный список опций — `tools/rpc/rpc-server.cpp:96-106`. Сервер отдаёт клиенту то, что сообщает
  устройство (`ggml/src/ggml-rpc/ggml-rpc.cpp:2419-2432`):
  - CUDA: `cudaMemGetInfo` (`ggml/src/ggml-cuda/ggml-cuda.cu:5654-5664`);
  - CPU на Linux: `free = total = физическая память` (`ggml/src/ggml-cpu/ggml-cpu.cpp:373-378`). Внутри WSL это вся память ВМ WSL,
    лимит пода k8s сюда не попадает.
- На лидере любое RPC-устройство имеет тип GPU, включая удалённый CPU (`ggml/src/ggml-rpc/ggml-rpc.cpp:2857-2861`). Поэтому слои
  на него попадают через `-ngl`, как на видеокарту. `supports_op` у RPC всегда `true` (`:2894-2899`), так что лидер не проверяет,
  умеет ли удалённое устройство операцию.

**Как ограничить память устройства (вывод).**
- **Лимит задаём на лидере через `--tensor-split`,** числами слоёв (раздел 5). Без `-ts` лидер делит слои по `free` устройств
  (`src/llama-model.cpp:1660-1677`). Удалённое CPU-устройство тогда получит долю по всей RAM WSL, а не по бюджету.
- **Жёсткая граница — `resources.limits.memory` пода rpc-сервера.** Буфер CPU выделяется через `malloc`, а Linux его не
  проверяет до первой записи. При перерасходе OOM-killer убьёт процесс посреди загрузки, и лидер упадёт. Лимит пода хотя бы
  ограничивает ущерб этим подом, а не всей WSL. Запас сверх бюджета — не меньше размера самого большого тензора, потому что
  `SET_TENSOR` целиком читается в `std::vector` (`ggml/src/ggml-rpc/ggml-rpc.cpp:344-358`, `:2606-2614`). При попадании в кэш в
  память целиком читается и файл кэша (`:1824-1841`).
- **Ограничения видеопамяти на сервере нет.** Если выделение не удалось, сервер отвечает `remote_ptr == 0`, а лидер печатает
  предупреждение и получает `nullptr` (`:995-1008`), то есть загрузка модели завершается ошибкой без зависания.
- **Риск Windows-драйвера.** В `docs/build.md:318` сказано, что в Windows есть настройка драйвера «System Memory Fallback». Влияет ли
  она на CUDA внутри WSL, по исходникам не проверить. Если влияет, перерасход VRAM не даст ошибку, а молча уйдёт в общую память и
  сильно замедлит работу. Проверить вживую (раздел 12).
- **Альтернатива: `--fit` + `--fit-target`.** `--fit` по умолчанию включён (`common/common.h:485`). Он держит на каждом устройстве
  свободный запас `margin` (`common/fit.cpp:729-731`), и для CPU через RPC запас `total − бюджет` дал бы точный потолок. Работает
  он только когда `-ngl` и `-ts` не заданы (`common/fit.cpp:544-556`). При нехватке он режет слои на части через переопределения
  тензоров (`:628-660`), а это выключает конвейер (раздел 5). Так он может сам разложить веса неудобным для сети образом.
  Рекомендация — `--fit off` и наш собственный `-ts`.

## 3. Предел 16 устройств и что с ним делать

**Проверено.**

| Где | Что | Цитата |
|---|---|---|
| Планировщик ggml | не больше 16 бэкендов, иначе `GGML_ASSERT` | `ggml/src/ggml-backend.cpp:1163-1164`, `:2217` |
| Лидер | бэкенды = устройства модели + ACCEL (у нас нет) + CPU | `src/llama-context.cpp:431-456` |
| `--tensor-split` | ошибка при 16 и более значениях, то есть максимум 15 | `common/arg.cpp:2801-2804` |
| Модель | хранит только 16 значений `tensor_split` и читает `n_devices()` значений | `src/llama-model.cpp:1361`, `:1660`, `:1679` |
| `--fit-target` | вектор на 16 значений | `common/common.h:490` |
| `GGML_RPC_MAX_SERVERS = 16` | объявлен, но нигде не используется | `ggml/include/ggml-rpc.h:17` (поиск по дереву других вхождений не нашёл) |

Итого на чистом b12033 на одного лидера приходится не больше 15 устройств. Порядок устройств в модели такой: сначала все RPC, потом
локальные GPU (`src/llama.cpp:275-279`). Лидер сейчас без своей видеокарты (`NVIDIA_VISIBLE_DEVICES=none`,
`portal/app/workloads/builders.py:302-312`), поэтому 15 нод с одним CUDA0 дают ровно 15 устройств и 16 бэкендов. Это работает,
но RAM нод при этом не используется.

Варианты (вывод, выбор за лидом или владельцем):

- **A. Пересобрать с поднятым пределом и отдать CUDA0 + CPU на всех 15 нодах (30 устройств).**
  - `GGML_SCHED_MAX_BACKENDS` обёрнут в `#ifndef` (`ggml/src/ggml-backend.cpp:1163`), его можно задать флагом компилятора без правки
    исходника: `-DCMAKE_CXX_FLAGS=-DGGML_SCHED_MAX_BACKENDS=64`.
  - `llama_max_devices()` возвращает литерал `16` (`src/llama.cpp:86-88`). Его нужно править `sed` в Dockerfile, например на 64.
    Массив `tensor_split` в `common` уже на 128 элементов (`common/common.h:484`), поэтому значения до 128 безопасны.
  - Других мест, зависящих от 16, в `src/`, `common/` и планировщике не найдено: поиск по `llama_max_devices` и
    `GGML_SCHED_MAX_BACKENDS`.
  - Это отступление от «чистого» b12033 в `global-constraints.md`, и его надо проверить сборкой и запуском (раздел 12).
- **B. Без пересборки: 15 нод, только CUDA0.** Ёмкость ≈ 15 × (12 ГиБ − резерв) ≈ 155 ГБ. DeepSeek 671B помещается только в IQ1.
- **C. Без пересборки: VRAM + RAM на 7 нодах.** 14 RPC-устройств + CPU лидера = 15 бэкендов. Ёмкость ≈ 7 × (10,5 + бюджет RAM),
  то есть меньше варианта B при бюджете RAM ~15 ГБ.
- **D. Без пересборки: лидер на главном, первые слои в его RAM.** `-ngl` меньше `n_layer + 1` оставляет первые
  `n_layer + 1 − ngl` слоёв на CPU лидера (`src/llama-model.cpp:1692-1698`). Это 15 GPU-нод плюс сотни ГБ RAM главного и один
  лишний сетевой переход на токен. Этот вариант противоречит решению «только split по классу» только если главный не должен
  считать, поэтому решение за владельцем.

## 4. Локальный кэш тензоров `-c` / `--cache`

**Проверено.**
- **Где лежит:** `fs_get_cache_directory() / "rpc"`. Это `$LLAMA_CACHE`, а без него `$XDG_CACHE_HOME/llama.cpp` или
  `~/.cache/llama.cpp` (`tools/rpc/rpc-server.cpp:58-77`, `:236-246`, `tools/rpc/README.md:96`). В образе ноды задано
  `LLAMA_CACHE=/var/lib/llm-models` (`node/Dockerfile`), значит кэш попадёт в `/var/lib/llm-models/rpc`. Сейчас rpc-под не
  монтирует этот путь (`portal/app/workloads/builders.py:289-299`), и кэш живёт в слое контейнера, пока под не пересоздан.
- **Как адресуется:** имя файла — 16 hex-символов 64-битного FNV-1a от содержимого тензора (`ggml/src/ggml-rpc/ggml-rpc.cpp:313`,
  `:1749-1754`). Каталог плоский. Смещение, имя тензора и модель в ключ не входят, поэтому одинаковые тензоры разных развёртываний
  делят один файл.
- **Что кэшируется:** только данные больше `HASH_THRESHOLD = 10 МиБ` в буферах весов (`GGML_BACKEND_BUFFER_USAGE_WEIGHTS`,
  `:117-118`, `:843-849`). Активации и KV в кэш не попадают.
- **Протокол загрузки тензора** (`:850-876`, асинхронный вариант `:1155-1180`):
  1. Лидер считает FNV по всем байтам тензора и шлёт `SET_TENSOR_HASH`.
  2. При попадании сервер читает файл и сам кладёт данные (`:1857-1891`), а данные по сети не идут.
  3. При промахе лидер шлёт `SET_TENSOR` с флагом сохранения, и сервер пишет файл (`:1748-1757`, `LOG_INFO "saved to"`).
- **Что важно для загрузки моделей.** Лидер грузит RPC-тензоры целиком одним `ggml_backend_tensor_set`, а не кусками по 1 МиБ:
  - асинхронная загрузка через pinned-буферы требует `host_buffer`, а у RPC `host_buffer = false`
    (`ggml/src/ggml-rpc/ggml-rpc.cpp:2865-2875`, `src/llama-model-loader.cpp:1624-1629`);
  - поэтому работают путь `mmap` (`src/llama-model-loader.cpp:1713-1749`) и путь без `mmap` (`:1817-1835`).

  Поэтому порог 10 МиБ применяется к тензору целиком, и кэш действительно работает для весов.
- **Вытеснения и лимита размера нет.** В коде нет удаления файлов. «cache evictions» в README (`tools/rpc/README.md:120`) относится к
  кэшу графов (`GRAPH_CACHE_MAX`, `ggml/src/ggml-rpc/ggml-rpc.cpp:120-122`, `:1260-1266`), а не к файлам.

**Поведение при повторной загрузке (вывод).**
- Сеть почти не нагружена, но лидер всё равно читает весь GGUF с диска и хэширует каждый тензор. Время повторного старта
  ограничено диском и CPU лидера, а не сетью.
- Файлы старых моделей остаются навсегда. Нужна внешняя очистка: по `atime`/`mtime` или при смене модели, с лимитом тома (2-3).
- Коллизия FNV-1a на 64 бита теоретически подменит тензор. Вероятность мала, но проверки целостности в коде нет.
- Сервер с `-c` пишет файл любого размера по запросу любого клиента. Это ещё одна причина держать порт 18050 закрытым снаружи (как
  сейчас, `node/run-node.sh:207`).

## 5. `--tensor-split`, `-ot`, `--cpu-moe` / `--n-cpu-moe` вместе с RPC

**`--tensor-split` (проверено).**
- Значения — доли через запятую или `/`, без нормировки на входе (`common/arg.cpp:2792-2815`).
- В модели они превращаются в накопленные доли (`src/llama-model.cpp:1682-1690`). Слой `il` идёт на первое устройство, чья
  накопленная доля больше `(il − i_gpu_start) / act_gpu_layers` (`:1692-1700`).
- Выходной слой (`output.weight`) считается слоем с номером `n_layer_all` и попадает на последнее устройство с ненулевой долей
  (`:1717`). Входной слой (`token_embd`) всегда на CPU лидера (`:1706-1708`).
- KV-кэш слоя лежит на устройстве этого слоя (`src/llama-kv-cache.cpp:215-219`).
- `-ngl all` (или `-ngl` больше `n_layer`) отдаёт устройствам все слои и выход (`src/llama-model.cpp:2452-2455`).
- Порядок устройств — порядок `--rpc`, внутри сервера — порядок его `-d` (`ggml/src/ggml-rpc/ggml-rpc.cpp:3156-3196`,
  `src/llama.cpp:229-276`). Локальные GPU лидера идут после RPC.
- Удобнее всего задавать `-ts` прямо числами слоёв. Так делает сам `--fit`: `tensor_split[id] = n_layer` (`common/fit.cpp:637`).
- Вывод: при сравнении `float` на границе возможен сдвиг на один слой. Фактическое размещение надо сверять по строкам лога
  `model buffer size`, `KV buffer size` и `compute buffer size` для каждого устройства (`src/llama-model.cpp:2043`,
  `src/llama-kv-cache.cpp:279`, `src/llama-context.cpp:859`).
- Вывод: слои неравны. У DeepSeek первые `leading_dense_block_count` слоёв плотные и меньше MoE-слоёв, у выходного слоя свой размер.
  Поэтому 2-2 должна считать байты каждого слоя по таблице тензоров GGUF (`blk.<i>.*`). Таблица идёт после всех KV, включая массивы
  токенизатора (`ggml/include/gguf.h:4-24`), и у каждого шарда своя. Сейчас парсер портала останавливается на ключах `tokenizer.*`.

**`-ot` / `--override-tensor` (проверено).**
- Формат: `<regex>=<тип буфера>,...`. Тип ищется среди буферов всех зарегистрированных устройств (`common/arg.cpp:228-262`). У RPC
  тип буфера называется `RPC<номер устройства на сервере>[host:port]`, например `RPC1[10.0.0.5:18050]`
  (`ggml/src/ggml-rpc/ggml-rpc.cpp:1327`).
- Переопределение побеждает размещение по слоям (`src/llama-model-loader.cpp:1247-1272`).
- Бэкенды создаются только для устройств модели и CPU (`src/llama-context.cpp:431-456`), поэтому RPC-устройство, указанное в
  `-ot`, тоже должно входить в модель. Через `-ot` обойти предел из раздела 3 нельзя (вывод).
- Любое переопределение выключает конвейерный параллелизм (`!model.has_tensor_overrides()`, `src/llama-context.cpp:528-534`). Это
  теряет перекрытие стадий при обработке промпта.

**`--cpu-moe` / `--n-cpu-moe` (проверено).** Оба флага переопределяют тензоры экспертов `\.ffn_(up|down|gate|gate_up)_(ch|)exps` в
`ggml_backend_cpu_buffer_type()` (`common/common.h:1257-1276`, `common/arg.cpp:2711-2726`). Это **CPU лидера**, а не CPU удалённой
ноды.

Вывод: с RPC это вредно. Каждый MoE-слой ходит «GPU удалённой ноды → CPU лидера → GPU удалённой ноды», то есть два сетевых
перехода на слой, и эксперты всех слоёв считает один процессор лидера. Флаги не рекомендуются. RAM нод подключаем как отдельное
устройство `CPU` в `-d` и даём ему целые слои.

**`--split-mode row|tensor` (проверено, коротко).** Прямой обмен сервер-сервер (`COMM_ALLREDUCE`) работает только для двух
RPC-бэкендов (`ggml/src/ggml-rpc/ggml-rpc.cpp:2999-3001`). Для 15 нод остаётся `layer`.

## 6. Сколько RPC-обменов на токен и задержка на 1 ГбЕ

**Что происходит на один шаг декодирования (проверено).**
- Граф делится на части по устройствам. Для каждой части планировщик:
  1. копирует входы (`ggml/src/ggml-backend.cpp:2146-2157`);
  2. запускает расчёт асинхронно (`:2159-2163`).
- У RPC нет `cpy_tensor_async` (`ggml/src/ggml-rpc/ggml-rpc.cpp:1312`), поэтому копия синхронная (`ggml/src/ggml-backend.cpp:2114-2122`):
  - `synchronize` у RPC — локальный барьер очереди, по сети он ничего не шлёт (`ggml/src/ggml-rpc/ggml-rpc.cpp:624-630`);
  - источник и приёмник на одном сервере: `COPY_TENSOR`, один запрос с ответом, данные по сети не идут (`:932-953`);
  - источник и приёмник на разных серверах: `GET_TENSOR` к источнику (запрос и ответ с данными) и `SET_TENSOR` к приёмнику
    (`ggml/src/ggml-backend.cpp:832-853`). Топология — звезда через лидера, ноды напрямую не общаются.
  - вход с хоста лидера (эмбеддинги, позиции, маска внимания): `SET_TENSOR` в одну сторону.
- Расчёт части — `GRAPH_COMPUTE` или короткий `GRAPH_RECOMPUTE` для уже виденного графа, тоже в одну сторону
  (`ggml/src/ggml-rpc/ggml-rpc.cpp:1248-1274`). Ответ `GET_TENSOR` приходит только после расчёта, потому что сервер обрабатывает
  команды по очереди (`:2480-2490`).
- В конце лидер забирает логиты с последнего устройства.

Ждущих обменов (round trip) на один шаг декодирования при `D` устройствах на `S` серверах, если устройства сервера идут подряд:
`(S − 1)` между серверами + `(D − S)` внутри серверов + 1 за логиты.

**Формула (расчёт).**

```
T_шаг ≈ Σ_d t_расч,d                                  (расчёт на устройствах, последовательно)
      + (S − 1) · (RTT + 2 · P · S_h / B)             (переходы между серверами через лидера)
      + (D − S) · RTT                                 (переходы CUDA0 → CPU внутри сервера)
      + D_уд · S_mask / B                             (маска внимания на каждое удалённое устройство)
      + RTT + P · S_logits / B                        (логиты с последнего устройства)
```

| Величина | Значение | Откуда |
|---|---|---|
| `B` | 125 МБ/с линейная скорость 1 Гбит/с; полезная по TCP при MTU 1500 ≈ 117 МБ/с (1448/1538) | расчёт |
| `S_h` | `n_embd × 4` байта на токен (остаточный поток f32) | вывод; `n_embd = 7168` у DeepSeek V3 и Kimi K2 — `config.json` |
| `S_logits` | `n_vocab × 4` байта на выходной токен | DeepSeek V3 `n_vocab = 129280` → 517 КБ; Kimi K2 `163840` → 655 КБ (`config.json`) |
| `S_mask` | `n_kv × P × 2` байта (f16 при flash attention, иначе f32) | `src/llama-graph.cpp:39-42` |
| `P` | токенов в шаге (одновременных запросов) | — |
| `RTT` | не измерено: в WSL2 через Docker и сеть k3s его надо мерить | `GGML_RPC_DEBUG=3` печатает время каждой команды (`tools/rpc/README.md:122`) |

**Порядок чисел без RTT** (расчёт, DeepSeek V3, `P = 1`, `n_kv = 8192`, `B = 117 МБ/с`):
- `S_h / B` = 28 672 / 117·10⁶ ≈ 0,25 мс;
- `S_logits / B` ≈ 4,4 мс;
- `S_mask / B` ≈ 0,14 мс.

Две конфигурации:
- **Вариант B** (15 серверов по одному CUDA0, лидер на первой ноде через loopback, 14 удалённых устройств):
  - сеть ≈ 15·RTT + 14·0,49 + 14·0,14 + 4,4 ≈ **15·RTT + 13 мс** на токен;
  - при RTT порядка десятых долей мс сетевой пол — 15–20 мс на токен, то есть до ~50–65 ток/с без учёта расчёта.
- **Вариант A** (15 серверов по CUDA0 + CPU, 30 устройств):
  - сеть ≈ **30·RTT + 15 мс**;
  - основная цена — не сеть, а расчёт той доли слоёв, что лежит в RAM: `t_расч` устройства CPU ≈ (байты активных весов его слоёв) /
    (пропускная способность RAM ноды). Её надо мерить на ПК класса.

**Обработка промпта** (расчёт, микробатч `n_ubatch = 512`, `common/common.h:461`):
- на каждый переход между серверами 2 · 512 · 28 672 Б ≈ 29 МБ, то есть ≈ 0,25 с;
- 14 переходов — ≈ 3,5 с на микробатч;
- маска на 14 удалённых устройств при `n_kv = 8192` — ещё до ≈ 1 с;
- итого до ~110–150 ток/с промпта на одной гигабитной сетевой карте лидера, если стадии не перекрываются.

Конвейер (`pipeline_parallel`, `src/llama-context.cpp:527-555`) может перекрыть расчёт стадий, но не трафик через сетевую карту
лидера. Поэтому лидер с 10 ГбЕ (например, главный) снял бы это ограничение.

## 9. Архитектуры и ключи GGUF для оценки KV-кэша

**Общее (проверено).**
- `n_layer_all = <arch>.block_count` (`src/llama-model.cpp:1415`), `n_layer = n_layer_all − <arch>.nextn_predict_layers`
  (`:1417`, `src/llama-hparams.cpp:348`).
- MTP/NextN-слои по умолчанию не грузятся: `load_mtp = false` (`common/common.h:593`), тензоры помечаются `TENSOR_SKIP`
  (`src/llama-model.cpp:3975-3977`). Их нет и в KV основного контекста (`:3296-3301`). Но они есть в размере файла, и оценка весов
  должна их вычесть.
- `head_count_kv` по умолчанию равен `head_count`, допускается массив по слоям (`src/llama-model.cpp:1489-1493`).
- `key_length` и `value_length` по умолчанию равны `n_embd / n_head` (`:1535-1539`).
- Размер KV на токен = Σ по слоям `< n_layer` от `(n_embd_k_gqa(il) + n_embd_v_gqa(il)) × байты типа`, где
  `n_embd_k_gqa = key_length × head_count_kv(il)` (`src/llama-hparams.cpp:156-166`, `src/llama-kv-cache.cpp:205-233`).
  Тип по умолчанию f16 (`-ctk`/`-ctv`, `common/arg.cpp:2388-2412`).

- `<arch>.leading_dense_block_count`;
- `<arch>.expert_count`, `<arch>.expert_used_count`;

Для `t_расч` из раздела 6 вес активных параметров на токен ≈ плотные части + общие эксперты + `expert_used_count / expert_count`
от тензоров экспертов. Это вывод, а не формула из кода.

Что поменять в портале (вывод, для 2-2):
- `kv_bytes` должен:
  - распознавать MLA по наличию обоих ключей `*_mla` и не считать V;

## 10. Прочее, что влияет на дизайн

- **Ошибка одного сервера валит лидера.** Любая ошибка сокета или неверный ответ ведут в `GGML_ABORT("Remote RPC server crashed or
  returned malformed response")` (`ggml/src/ggml-rpc/ggml-rpc.cpp:31`, `:683-689`). Если команда на сервере не прошла, он закрывает
  соединение (например, `:2606-2614`). Значит, потеря любой из 15 нод роняет всю группу, а лидер перезапускается. Это касается 2-4:
  резерв и пауза перед пересборкой.
- **Один клиент за раз** (`:2823-2832`). Пока лидер держит соединение, второй клиент ждёт в очереди `accept`. Портал это уже
  учитывает (`portal/app/workloads/builders.py:281-286`).
- **Неудачное выделение памяти завершает загрузку ошибкой без зависания** (`:995-1008`): llama-server выходит с
  `exiting due to model loading error` (`tools/server/server.cpp:672-677`).
- **Двойной проход `--fit`.** `--fit` по умолчанию включён и перед загрузкой делает пробный проход с `no_alloc`: строит модель и
  контекст, обращаясь к RPC-серверам (`common/fit.cpp:342-345`, `common/common.cpp:1312`). При заданном `-ngl` он в итоге
  отказывается менять параметры с предупреждением (`common/fit.cpp:544-545`, `:975-977`), но время уже потрачено. При пересборке
  с более чем 16 устройствами он ещё и читает 16-элементный `fit_params_target` за границей (`common/fit.cpp:369-371`). Нужен
  `--fit off`.
- **Режим загрузки `auto` = mmap.** RPC объявляет `mmap_support = true` (`ggml/src/ggml-rpc/ggml-rpc.cpp:2874`,
  `src/llama-model.cpp:1615-1624`). Лидер отображает весь файл в память и читает тензоры через page cache. На ноде лидера это давит
  на RAM, общую с локальным rpc-сервером, но страницы вытесняемые (вывод).

## 11. Рекомендуемая конфигурация

Решение, которое нужно от лида до 2-2: **вариант A (пересборка с поднятым пределом) или B (без пересборки)** из раздела 3.
Рекомендую A, потому что цель «Q2 на 671B» без RAM нод недостижима (раздел «Ёмкость» плана). Ниже обе конфигурации. Они отличаются
только `-d` у rpc-сервера и длиной `-ts`.

### 11.1. Сборка (только вариант A)

В `node/Dockerfile`, в обеих стадиях `build-*`, после `git clone` (вывод, проверить сборкой):

```dockerfile
RUN sed -i '/^size_t llama_max_devices(void) {$/{n;s/return 16;/return 64;/}' src/llama.cpp \
 && grep -A1 '^size_t llama_max_devices(void) {$' src/llama.cpp | grep -q 'return 64;'
# и в cmake -B build ...:
#   -DCMAKE_CXX_FLAGS=-DGGML_SCHED_MAX_BACKENDS=64
```

Проверка после сборки: `llama-server --rpc <30 устройств> -ts <30 значений>` стартует, и в логе 30 строк `using device RPC<n>`
(`src/llama.cpp:303-309`).

### 11.2. rpc-сервер на каждой из 15 нод

```bash
LLAMA_CACHE=/var/lib/llm-models \
ggml-rpc-server -H 0.0.0.0 -p 18050 -d CUDA0,CPU -t <число физических ядер> -c   # вариант A
ggml-rpc-server -H 0.0.0.0 -p 18050 -d CUDA0     -t <число физических ядер> -c   # вариант B
```

- `-d CUDA0,CPU`: CUDA0 получает серверный номер 0, CPU — номер 1. Порядок важен для `-ts` и имён буферов `RPC0[...]`/`RPC1[...]`.
- `-c`: кэш в `/var/lib/llm-models/rpc`. rpc-поду нужен тот же `hostPath` `llm-models`, что у инференса, и внешняя очистка по
  лимиту (2-3).
- `-t`: потоки CPU-устройства. Один процесс обслуживает оба устройства последовательно, лишние потоки не помогают.
- Под: `resources.limits.memory = RAM_BUDGET + запас`, запас не меньше самого большого тензора модели плюс 1 ГиБ
  (раздел 2). На ноде лидера `RAM_BUDGET` уменьшить на память лидера: `token_embd`, буфер логитов, compute-буфер CPU.

### 11.3. Лидер (одна группа из 15 нод)

```bash
NVIDIA_VISIBLE_DEVICES=none \
llama-server -m /var/lib/llm-models/<repo>/<файл>-00001-of-0000N.gguf \
  --rpc 127.0.0.1:18050,<ip2>:18050,...,<ip15>:18050 \
  -ngl all --split-mode layer \
  --tensor-split <g1>,<c1>,<g2>,<c2>,...,<g15>,0 \
  --fit off -fa auto \
  --ctx-size <ctx_per_request × parallel> --parallel <parallel> --no-kv-unified \
  ...прочие флаги serve-llama.sh без изменений
```

- `--rpc`: первым идёт свой узел по loopback (как сейчас в `split_leader`), дальше остальные в фиксированном порядке. Этот же
  порядок задаёт смысл `-ts`.
- `--tensor-split`: **целые числа слоёв** на каждое устройство в порядке `[сервер1.CUDA0, сервер1.CPU, сервер2.CUDA0, ...]`.
  Сумма — `n_layer_all + 1`, последняя единица — выходной слой.
  - Последнему CPU-устройству ставим 0. Тогда выходной слой (большая матрица `n_embd × n_vocab`) ляжет на CUDA0 последней ноды, а
    не на её процессор (раздел 5).
  - Вариант B: 15 значений, только `g1..g15`.
- `-ngl all`: все слои и выход на RPC-устройства. На CPU лидера остаётся `token_embd`.

  (`common/arg.cpp:2640`, `:2766`, `:2817`, `:2841`).

### 11.4. Как посчитать лимит каждого устройства (для 2-2)

1. **Бюджеты.**
   - `budget(CUDA0) = VRAM − 1,5 ГиБ` (как `NVIDIA_RESERVE` в `estimate.py`) − compute-буфер устройства. Compute-буфер последнего
     устройства больше: там логиты микробатча `n_vocab × n_ubatch × 4` Б, у DeepSeek ≈ 265 МБ (расчёт).
   - `budget(CPU) = RAM_BUDGET` ноды (метка `llm.nsu/ram-mib`, по умолчанию 70 % RAM WSL).
2. **Стоимость слоя.** `cost(il)` = сумма `ggml_nbytes` тензоров `blk.<il>.*` из таблиц тензоров всех шардов, без MTP-слоёв, плюс
   KV слоя. KV слоя = `ctx_total × (k + v) × 2` Б, для MLA `v = 0`. `cost(output)` = `output.weight` + `output_norm`.
3. **Раскладка.** Слои по порядку жадно заполняют устройства в порядке `-ts`. Устройство берёт слои, пока сумма не превышает его
   бюджет. Число слоёв каждого устройства и есть его значение в `-ts`. Если слои кончились раньше устройств, хвостовые устройства
   получают 0. Если устройства кончились раньше слоёв, модель не помещается.
4. **Проверка после старта.** Контроллер читает из лога лидера строки `model buffer size`, `KV buffer size` и
   `compute buffer size` по каждому `RPC<n>[ip:port]` и сравнивает с расчётом. Расхождение больше одного слоя — повод для
   предупреждения.

## 12. Что проверить вживую (ноутбук владельца, newbar)

1. Вариант A: сборка с `GGML_SCHED_MAX_BACKENDS=64` и `llama_max_devices() = 64`, старт лидера на 17 и больше RPC-устройствах.
   Достаточно нескольких rpc-серверов с `-d CUDA0,CPU` или `-d CPU` на newbar и тестовой модели. Отдельно проверить, что `-ts` из
   целых чисел даёт ровно заданные слои, по строкам `model buffer size`.
2. `-d CUDA0,CPU` в WSL2 на RTX 4070: два устройства видны лидеру, слои на CPU-устройстве считаются.
3. Поведение при перерасходе VRAM в WSL: ошибка выделения или тихий уход в общую память («System Memory Fallback»,
   `docs/build.md:318`).
4. RTT и время команд между нодами в сети k3s через WSL2/Docker: `GGML_RPC_DEBUG=3` на лидере вместе с `-lv 5`
   (`tools/rpc/README.md:116-136`). Числа подставить в формулу раздела 6.
5. Кэш `-c`: при второй загрузке на rpc-нодах нет новых файлов, сетевой трафик лидера мал, а время старта определяется чтением файла
   на лидере.
