# Нагрузочный тест: 1000 одновременных пользователей

Набор проверяет требование владельца: система держит 1000 одновременных активных пользователей (интерфейс, API, генерации) без падений; генерации честно встают в очередь по слотам узлов; перегрузка возвращает понятный 429 (`Retry-After`, русское сообщение), а не таймауты и 5xx; пропускная способность измеряется.

| Файл | Где запускается | Что делает |
| --- | --- | --- |
| `prepare.py` | внутри контейнера `llm-main` (только stdlib) | создаёт пользователей `loadtest-<i>` с ключами, регистрирует тестовые бэкенды, удаляет всё созданное |
| `fake_backends.py` | хост нагрузки | запускает K тестовых OpenAI-бэкендов (`portal/tests/fakes/openai_backend.py`) |
| `run.py` | хост нагрузки | генератор нагрузки: asyncio, один процесс, один пул соединений |
| `report.py` | где угодно | сводка по `results.jsonl`, пишет `results.md` |

## Подготовка хоста нагрузки

Python 3.11 или новее. Хост должен видеть основной сервер по 443 и быть достижим с main по портам 28100 и выше (сценарий A).

```
cd loadtest
python -m venv .venv
.venv/bin/pip install -r requirements.txt        # Windows: .venv\Scripts\pip
ulimit -n 4096                                    # каждое соединение занимает файловый дескриптор; run.py пытается поднять лимит сам
```

Один процесс `run.py` держит 1000 потоков SSE (пул на users + 100 соединений, HTTP/1.1 keep-alive, без потоков ОС). Сам генератор тоже может стать узким местом, и тогда он искажает TTFT и задержки. Признак: лаг цикла событий (насколько позже срабатывает таймер; замер каждые 0,5 с). Он печатается в строке прогресса, а `report.py` при p95 лага выше 200 мс пишет «генератор перегружен». Дополнительные признаки: ошибки класса `pool` и `client_overload`. Тогда разделите пользователей между процессами или хостами:

```
python run.py ... --users 1000 --shard 1/2 --out r1.jsonl     # на хосте или процессе 1
python run.py ... --users 1000 --shard 2/2 --out r2.jsonl     # на хосте или процессе 2
python report.py r1.jsonl r2.jsonl                            # общий отчёт
```

`--shard I/N` запускает пользователей с индексами I-1, I-1+N, ... из `--users`; остальные параметры (`--users`, `--ramp`, `--keys`, `--seed`) одинаковы, долю `--portal-rps` процессы делят поровну. Запускайте шарды одновременно (часы хостов должны совпадать, например по NTP), иначе максимум одновременных запросов в объединённом отчёте будет неверным.

## Подготовка LiteLLM (на main)

```
docker cp loadtest llm-main:/opt/llm/loadtest
docker exec llm-main python3 /opt/llm/loadtest/prepare.py create --users 1000 --rpm 600 --out /tmp/keys.json
docker cp llm-main:/tmp/keys.json ./keys.json && docker exec llm-main rm /tmp/keys.json
```

`keys.json` содержит рабочие ключи (права 600, в `.gitignore`); `prepare.py` ничего секретного не печатает. Главный ключ берётся из `/var/lib/llm/secrets.env` (`LITELLM_MASTER_KEY`). У ключей `metadata.loadtest=true`, высокие `rpm` и `tpm`, чтобы упираться в кластер, а не в лимиты ключа.

## Сценарий A: только шлюз (Caddy, LiteLLM, Postgres, Redis)

Модель-пустышка с настраиваемой скоростью токенов; проверяет, что шлюз держит 1000 одновременных потоков.

```
# хост нагрузки: 4 бэкенда, 50 мс на токен, ответ дополняется до max_tokens
python fake_backends.py --count 4 --port-base 28100 --delay-ms 50 --advertise-ip <IP хоста нагрузки>
# напечатает строку --api-base ...; затем на main:
docker exec llm-main python3 /opt/llm/loadtest/prepare.py register-backends --model lt-fake \
    --api-base http://<IP>:28100/v1 --api-base http://<IP>:28101/v1 --api-base http://<IP>:28102/v1 --api-base http://<IP>:28103/v1
# прогон
python run.py --base https://<host> --resolve <host>:<IP main> --cacert ca.crt --keys keys.json \
    --model lt-fake --users 1000 --ramp 60 --duration 300 --max-tokens 64 --stream --out results.jsonl
python report.py results.jsonl
```

Поток одного запроса длится примерно `(max_tokens + 1) * delay_ms`: при 64 токенах и 50 мс это 3,3 с плюс 1–3 с паузы, поэтому одновременно в полёте будет около 70% пользователей. Чтобы дойти до 1000 параллельных потоков, увеличьте `--delay-ms` или `--max-tokens`. Один процесс тестового бэкенда сам становится узким местом при сотнях потоков (его TTFT растёт): запускайте несколько бэкендов, смотрите в отчёте на p50 TTFT при малой нагрузке и сравнивайте.

Тестовые бэкенды регистрируются напрямую в LiteLLM главным ключом и не управляются порталом (`portal_managed` нет, поэтому контроллер их не трогает). Убрать их: `prepare.py cleanup` (удаляет и бэкенды, и ключи, и пользователей).

## Сценарий B: настоящий кластер

Маленькие модели (например `ggml-org/gemma-3-270m-it-GGUF`) на узлах 122b и ноутбука через портал (`parallel` равен числу слотов). Дальше тот же `run.py`, `--model` — имя развёртывания. Цель: ограниченные очереди и 429 с `Retry-After` при перегрузке, ни одного 5xx и таймаута.

Трафик портала (интерфейс) добавляется вместе с запросами к моделям:

```
python run.py ... --portal-cookie-file cookie.txt --portal-rps 20
```

В `cookie.txt` значение cookie `nsullm_session` залогиненного пользователя (или `nsullm_session=...`). Запросы идут к `/api/me`, `/api/models`, `/api/keys` с равномерной частотой, независимо от ответов.

## Параметры `run.py`

- `--users N` виртуальных пользователей; каждый в цикле: запрос, пауза `--think-min`..`--think-max` (по умолчанию 1–3 с). Ключей может быть меньше, чем пользователей: ключи используются по кругу.
- `--ramp S` пользователи стартуют равномерно за S секунд; `--duration S` время под полной нагрузкой после разгона. Незавершённые запросы дожидаются.
- `--stream` потоковые ответы; без него TTFT не меряется.
- `--request-timeout S` предел на один запрос целиком (по умолчанию 120 с); сюда входит ожидание в очереди.
- `--honor-retry-after` после ответа 429 ждать `Retry-After` (±20%) вместо паузы `--think-min`..`--think-max`, как это делает клиент OpenAI SDK. По умолчанию выключено: без него пользователи повторяют запрос через 1–3 с, это худший случай для шлюза.
- `--prompt-tokens`, `--max-tokens` размер запроса и ответа (токены приблизительно равны словам).
- `--resolve host:ip`, `--cacert F` как в `e2e/`: подключение к IP при проверке сертификата по имени.

В `results.jsonl` одна строка на запрос: `kind`, `user`, `start`, `end`, `latency`, `ttft` (до первого SSE-чанка с данными), `status` (0 если ответа не было), `error`, `tokens`, `retry_after`, `msg`. Классы `error`: `http` (смотрите `status`), `timeout`, `connect`, `protocol` (обрыв, поток без `[DONE]`), `stream_error` (ошибка внутри потока), `pool` (на стороне генератора нет свободного соединения), `client_overload` (генератор не успевает слать трафик портала), `other`. Строки `kind: loop_lag` это замеры лага цикла событий, а не запросы.

## Как читать отчёт

`report.py` печатает и пишет `results.md`: итоги, число успешных, 429 (сколько из них с `Retry-After`), 5xx, таймаутов, ошибок соединения; p50, p95 и p99 для TTFT и полной задержки по успешным запросам; токены в секунду; максимум одновременных запросов; лаг цикла событий генератора и отметку о его перегрузке; примеры ошибок. Принимает несколько файлов (шарды). Успех по требованию: 5xx, таймаутов и ошибок соединения нет, все отказы это 429 с `Retry-After`, максимум одновременных близок к `--users`.

## Уборка

```
docker exec llm-main python3 /opt/llm/loadtest/prepare.py cleanup
```

Удаляет только ключи и пользователей, у которых и имя начинается с `loadtest-`, и `metadata.loadtest=true`, и тестовые бэкенды с `model_info.loadtest=true`. Потом остановите `fake_backends.py` и удалите `keys.json`.

## Тесты

`.venv/bin/python -m pytest -q` в каталоге `loadtest/`: офлайн, без сети (respx, локальный фиктивный LiteLLM). Они не заменяют прогон: эндпоинты `/key/list`, `/user/list`, `/user/delete` проверены только на фиктивном LiteLLM. Перед большим прогоном выполните `create --users 2` и `cleanup` на живом шлюзе и убедитесь, что `cleanup` печатает `ключей 2, пользователей 2`.
